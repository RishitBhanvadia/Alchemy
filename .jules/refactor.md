## 2024-03-07 - Declarative Side-Effects Instead of Imperative Handlers
**Before:** Duplicate event handlers (`handleChemAChange`, `handleChemBChange`, etc.) were used to imperatively call a side-effect function (`change_tip()`) immediately after triggering a state update (`setChemX()`). The side-effect function itself contained a deeply nested if/else block checking the 4 pieces of state to determine a tip color via another state variable `tcolor`.
**Issue:** This imperative approach caused unnecessary code duplication (4 identical handlers). More importantly, calling a side-effect synchronously inside an event handler right after setting state is an anti-pattern in React and is prone to stale closures and race conditions since the state update is asynchronous. Also, setting state in an effect causes cascading renders.
**Learning:** By removing the `tcolor` state and calculating it synchronously during the render pass based on the `chemA/B/C/D` states, we adhere to React's derived state paradigm. This completely eliminates cascading renders, the `useState` hook, the side-effect `useLayoutEffect`, and allows the event handlers to be perfectly inlined. It also cleanly flattens the nested if/else blocks into readable `if/else if` statements.
